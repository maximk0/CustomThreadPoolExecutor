# Отчет по курсовой работе
# Разработка и исследование собственного пула потоков

## Введение
В рамках курсовой работы был разработан собственный пул потоков `CustomThreadPoolExecutor`, реализующий интерфейс `CustomExecutor`.
Пул поддерживает настраиваемые параметры: 
- `corePoolSize`, 
- `maxPoolSize`, 
- `keepAliveTime`, 
- `queueSize` (емкость очереди каждого воркера), 
- `minSpareThreads` (минимальное количество резервных потоков). 

Для балансировки задач используется алгоритм **Round Robin** между воркерами, каждый из которых имеет собственную очередь `ArrayBlockingQueue`. 

Политика отказа специфицирована интерфейсом `CustomRejectionPolicy`.
В демонстрации используется реализация `CustomCallerRunsPolicy`, выполняющая задачу в вызывающем потоке при переполнении.

В отчете представлен анализ бенчмарков производительности разработанного пула в сравнении со стандартными реализациями (`ThreadPoolExecutor`, `ForkJoinPool`),
а также при разных комбинациях параметров.

## Анализ производительности

Для сравнения производительности использовались бенчмарки, выполненные с помощью JMH. 
Измерялось среднее время выполнения задачи подсчета простых чисел в диапазоне от 1 до 10000, разбитой на 64 подзадачи. 
Все пулы работали с 8-ю потоками.

### Результаты сравнения

|           Пул            | Среднее время, мкс/оп |  Ошибка (99.9%)  |
|:------------------------:|:---------------------:|:----------------:|
|    ThreadPoolExecutor    |         35.22         |      ±31.43      |
|       ForkJoinPool       |         37.66         |      ±12.20      |
| CustomThreadPoolExecutor |        141.05         |     ±153.03      |
*Данные из бенчмарка PoolsBenchmark (range=10000, tasks=64, threads=8).*

## Интерпретация
`ThreadPoolExecutor` и `ForkJoinPool` показывают близкие результаты (ок. 35–38 мкс/оп).
   Это объясняется высокой степенью оптимизации стандартных реализаций: эффективное управление потоками и минимальные накладные расходы на синхронизацию.
`CustomThreadPoolExecutor` оказался примерно в 4 раза медленнее (141 мкс/оп). 

Основные причины:
1.   Накладные расходы на распределение задач:
      - выбор воркера по **Round Robin** требует захвата `lock` для доступа к списку `workers`;
      - после выбора воркера выполняется `queue.offer(task)`. `ArrayBlockingQueue` использует внутренние блокировки, что добавляет синхронизацию на каждый вызов.
2.   Отсутствие work-stealing: если у одного воркера очередь переполнена, а у другого пуста, задачи не могут быть перераспределены. 
В `ForkJoinPool` кража задач автоматически выравнивает нагрузку. 
В разработанном пуле это приводит к простоям потоков и увеличению общего времени выполнения.

Таким образом, разработанный пул уступает стандартным аналогам по скорости, но предоставляет гибкость кастомизации (отдельные очереди, `minSpareThreads`, расширенное логирование), что может быть полезно в специализированных сценариях.

## Мини-исследование влияния параметров
Для исследования влияния параметров на производительность был проведен бенчмарк `CustomPoolTuning`, в котором варьировались:
- `tasks` – количество подзадач (8, 32, 64); 
- `threads` – количество потоков в пуле (12, 16, 20); 
- `queueSize` – емкость очереди каждого воркера (4, 32, 128); 
- `minSpareThreads` – минимальное количество резервных потоков (0, 1, 5).

Во всех экспериментах `corePoolSize` = `maxPoolSize` = `threads`, поэтому пул работал со статическим числом потоков. 
minSpareThreads в таких условиях не создает дополнительные потоки, так как количество запущенных потоков уже не меньше заданного значения.

### Влияние количества задач (`tasks`)
При фиксированных `threads = 12`, `queueSize = 4`, `minSpareThreads = 0`:

| tasks | Среднее время, <br/>мкс/оп |
|:-----:|:--------------------------:|
|   8   |           32.99            |
|  32   |           74.63            |
|  64   |           137.84           |

Увеличение числа задач приводит к почти линейному росту времени выполнения (соотношение 1:2.3:4.2). 
Это ожидаемо, так как каждая задача требует выполнения работы по проверке чисел на простоту.

### Влияние количества потоков (threads)
При `tasks = 64`, `queueSize = 128`, `minSpareThreads = 0`:

| threads | Среднее время, <br/>мкс/оп |
|:-------:|:--------------------------:|
|   12    |           131.79           |
|   16    |           136.99           |
|   20    |           157.39           |

Увеличение числа потоков с 12 до 20 не улучшило производительность, а даже ухудшило. 
Причины: 
- конкуренция за общие ресурсы (синхронизация на `lock` при доступе к списку воркеров)
- ограниченное количество вычислительных ядер (бенчмарк запускался на системе с 10-ю ядрами процессора). 

Лишние потоки увеличивают накладные расходы на переключение контекста.

### Влияние размера очереди (queueSize)
При `tasks = 64`, `threads = 12`, `minSpareThreads = 0`:

| queueSize | 	Среднее время, мкс/оп | 
|:---------:|:----------------------:|
|    4	     |         137.84         | 
|    32     |         131.75         | 
|    128    |         131.79         | 

Увеличение очереди с 4 до 32 дало небольшое снижение времени (возможно, из-за уменьшения вероятности отказа и повторных попыток). 
Дальнейшее увеличение до 128 не принесло выигрыша, так как все задачи успешно помещались в очереди и без больших запасов.

### Влияние `minSpareThreads`
Поскольку в бенчмарке `corePoolSize` = `maxPoolSize`, параметр `minSpareThreads` не оказывал влияния на количество потоков. 
Однако в динамических сценариях (когда `corePoolSize` < `maxPoolSize`) этот параметр позволил бы поддерживать заданное число свободных потоков, что могло бы уменьшить задержки при внезапных пиках нагрузки.

## Принцип распределения задач и балансировки
Разработанный пул использует подход «один воркер – одна очередь». 
Каждый воркер (`Worker`) имеет собственную очередь (`ArrayBlockingQueue`) фиксированной емкости (`queueSize`).

- Распределение задач происходит по алгоритму **Round Robin**: при поступлении задачи выбирается следующий по кругу воркер из списка workers, и задача помещается в его очередь. 
- Если очередь выбранного воркера переполнена, пул пытается добавить новый поток (если `workers.size()` < `maxPoolSize`) и предложить задачу ему. В случае неудачи срабатывает политика отказа. 
- Алгоритм **Round Robin** обеспечивает простую балансировку, но не учитывает текущую загруженность воркеров. Это может приводить к ситуации, когда один воркер перегружен, а другой простаивает, однако для многих сценариев такой подход достаточен.

Дополнительная балансировка реализована через механизм `minSpareThreads`: если количество свободных потоков падает ниже заданного порога, создаются новые потоки (до `maxPoolSize`), что позволяет быстрее реагировать на рост нагрузки.

## Заключение
В ходе работы был создан кастомизируемый пул потоков с гибкой настройкой, поддержкой `minSpareThreads`, политикой отказа и логированием. 
Бенчмарки показали, что по производительности он уступает стандартным реализациям из-за накладных расходов на распределение задач и синхронизацию.

`CustomThreadPoolExecutor` может использоваться в серверном приложении для управления задачами,
обработки входящих запросов, расчётов, взаимодействия с другими сервисами и хранилищами.
Архитектура с несколькими очередями и распределением задач по алгоритму **Round Robin** позволяет равномерно
распределять нагрузку между worker-потоками без общей точки конкуренции в виде одной очереди.

Параметры `corePoolSize`, `maxPoolSize` и `keepAliveTime` дают возможность управлять количеством активных потоков
в зависимости от текущей нагрузки, а `minSpareThreads` позволяет поддерживать резерв готовых к работе потоков
для снижения задержки при всплесках запросов. Ограничение `queueSize` защищает систему от бесконтрольного накопления задач в памяти,
а политика `CallerRuns` реализует backpressure и переводит систему в контролируемый режим деградации при перегрузке.

Дополнительно кастомная `ThreadFactory` и подробное логирование упрощают трассировку жизненного цикла потоков,
анализ отказов и диагностику поведения пула под нагрузкой.

## Демонстрационная программа
Для проверки корректности работы пула в классе `Main` инициализируется пул с параметрами `corePoolSize = 2`, `maxPoolSize = 4`, `queueSize = 2` (емкость очереди каждого воркера), `keepAliveTime = 5` сек и `minSpareThreads = 1`. 

В пул отправляются 10 Runnable задач с длительностью 3 секунды и 3 Callable задачи. 
Из-за ограниченной емкости очередей часть задач не помещается и выполняется в вызывающем потоке (политика `CallerRuns`), что демонстрирует механизм отказа. 

После завершения задач вызывается `shutdown()`, и по истечении таймаута останавливаются лишние потоки, оставляя только `corePoolSize` воркеров, что подтверждается выводом счетчиков. 
Логирование фиксирует все ключевые события: создание и завершение потоков, принятие задач в очереди, выполнение, таймауты и отказы.
